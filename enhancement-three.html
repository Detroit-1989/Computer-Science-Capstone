Enhancement Three Narrative

Artifact: Travlr Getaways · MongoDB, Mongoose, and REST API enhancements

Artifact Description

The artifact selected for the database category is the Travlr Getaways full-stack web application, originally developed in CS 465: Full Stack Development in 2026. Travlr is a MEAN-stack application that uses MongoDB, Express.js, Angular, and Node.js. The application includes a customer-facing website and an administrative interface for managing vacation packages.

MongoDB provides persistent storage for the vacation-package records. Mongoose is used to define the application data model and establish communication between MongoDB and the server-side application. Express and Node.js provide RESTful API endpoints, while Angular provides the administrative user interface.

The original application supported the fundamental create, read, update, and delete operations needed to manage vacation packages. For the CS 499 database enhancement, I expanded the dataset to 20 vacation packages and strengthened the database functionality by improving schema validation and implementing database-side filtering and sorting through the REST API.

Justification for Inclusion and Description of the Enhancement

I selected the Travlr application because it demonstrates how a database functions as an integrated component of a complete software system rather than as an isolated storage mechanism. The artifact combines persistent data storage, schema modeling, API development, authentication, validation, and user-interface functionality.

One of the strongest aspects of the artifact is the relationship between MongoDB, Mongoose, Express, and Angular. Vacation-package information is stored as MongoDB documents. Mongoose defines how the application interprets those documents, Express exposes database operations through RESTful endpoints, and Angular consumes those endpoints to display and manage the information.

The original GET /api/trips operation retrieved the complete trip collection. I enhanced this operation so that the server can construct MongoDB queries from URL query parameters. The enhanced endpoint supports filtering vacation packages according to a maximum price and sorting records according to several criteria.

/api/trips?maxPrice=2000
/api/trips?sort=priceLow
/api/trips?sort=priceHigh
/api/trips?maxPrice=2000&sort=priceLow

The maximum-price query returns only vacation packages whose per-person price does not exceed the requested threshold. Sorting can be performed in ascending or descending numerical price order, and filtering and sorting can be combined in the same request. I also added query validation so that a negative maximum price is rejected with an HTTP 400 response rather than being passed into the database query.

/api/trips?maxPrice=-100

An important improvement involved the Mongoose schema for the perPerson field. During testing, I discovered that the field had originally been defined as a String in the Mongoose schema even though MongoDB stored the vacation-package prices as numeric values. This mismatch caused inconsistent behavior when filtering and sorting records through the API.

perPerson: {
    type: Number,
    required: true,
    min: 0
}

Changing perPerson to Number aligned the application model with the actual MongoDB data and added validation that prevents negative trip prices. I verified the existing MongoDB collection using aggregation and direct queries. The collection contained 16 integer price values and four double values, so all 20 prices were already stored as numeric BSON types. A direct MongoDB query confirmed that 15 vacation packages met the $2,000 maximum-price condition. After the Mongoose schema correction, the REST API returned those same 15 records successfully.

Together, these improvements demonstrate database modeling, persistent storage, validation, query construction, RESTful API design, data integrity, and full-stack database integration.

Reflection on the Enhancement Process

One of the most important lessons I learned from this enhancement was that successful database development involves more than writing queries. The data model, database values, API controller, validation rules, and application code must agree about the meaning and type of stored information.

A significant challenge occurred while implementing numerical price filtering. Direct MongoDB queries correctly identified 15 vacation packages priced at $2,000 or less, but the REST API initially returned inconsistent results. I used MongoDB aggregation operations to inspect the BSON types of the perPerson values and found 16 integers and four doubles, confirming that all 20 values were numeric.

The investigation then moved to the application layer. I inspected the Mongoose model and discovered that perPerson had been defined as a String. This created a mismatch between the database and application schemas. Changing perPerson to Number resolved the discrepancy and allowed the API to perform the same numerical filtering and sorting as MongoDB.

This debugging process strengthened my understanding of data integrity and schema consistency. Even when stored database values are correct, an incorrect application-level schema can affect how queries are cast and interpreted. I also gained additional experience troubleshooting a multi-layer application by distinguishing among MongoDB, Mongoose, Express routing, API controllers, and Node.js runtime issues.

Another challenge involved stale Node.js processes that remained bound to port 3000 while newer application changes were being tested. Identifying and terminating those processes demonstrated how runtime and environment problems can resemble source-code defects. This reinforced the importance of verifying the execution environment during debugging.

The enhancement also strengthened my understanding of the difference between client-side processing and database-side processing. The application can now perform filtering and sorting directly through MongoDB queries before records are returned through the REST API. This reduces unnecessary processing at the presentation layer and demonstrates a clearer separation of responsibilities between the database, server, and client components.

Overall, this enhancement gave me practical experience with MongoDB queries, Mongoose schemas, RESTful APIs, CRUD operations, validation, authentication, debugging, and data-integrity analysis. More importantly, it strengthened my understanding of how database design decisions influence an entire full-stack application. These skills will be valuable as I continue developing software applications and pursue work involving data analytics and data science.
